# Упрощение кода — параллельное ревью и чистка

Проверь свои недавние изменения четырьмя сфокусированными ревьюерами,
работающими параллельно, агрегируй находки и примени фиксы, которые стоит
применить.

**Это проход чистки, не охота за багами.** Ты улучшаешь качество уже
работающего кода — убираешь дублирование, сплющиваешь ненужную сложность,
режешь потери, углубляешь заплатки. Не охоться здесь на баги корректности —
для этого отдельное ревью (см. `code-review-ru`, `security-audit-ru`).

**Ключевой принцип:** четыре узких ревьюера лучше одного широкого. Каждый
глубоко ищет в кодовой базе один класс проблем — переиспользование, качество,
эффективность, глубина, — не размывая внимание на все четыре. Они работают
параллельно, так что платишь задержку одного ревью, а не четырёх.

## Когда использовать

Запускай, когда пользователь говорит что-то из:

- «упрости» / «упрости мои изменения»
- «поревьюй мой код» / «поревьюй недавние изменения» / «почисти изменения»
- «/simplify»

Опциональные модификаторы — соблюдай их:

- **Фокус:** «упрости с фокусом на эффективность» → запусти только ревьюера
  эффективности (или взвесь агрегацию в его пользу). Распознаваемые фокусы:
  `reuse`, `quality` (принимает и `simplification`), `efficiency`, `altitude`.
- **Сухой прогон:** «упрости, но ничего не меняй» / «только отчёт» → прогони
  четырёх ревьюеров, представь находки, НЕ применяй ничего. Спроси перед
  применением.
- **Область:** «упрости последний коммит» / «упрости staged» / «упрости
  src/foo.py» → сузь источник diff соответственно (см. фазу 1).

НЕ запускай это автоматически после каждой правки и не приклеивай в конец
несвязанных задач. Это стоит четыре субагента токенов — вызывай только по
явной просьбе пользователя.

## Процесс

### Фаза 1 — Определи изменения

Захвати diff для ревью. Источник — по запросу пользователя, в этом порядке
по умолчанию:

```bash
# 1. По умолчанию: незакоммиченные изменения рабочего дерева (отслеживаемые файлы)
git diff

# 2. Если пусто — включая staged
git diff HEAD

# 3. Варианты области, которые может запросить пользователь:
git diff --staged                 # "staged-изменения"
git diff HEAD~1                    # "последний коммит"
git diff main...HEAD              # "эта ветка" / "мой PR"
git diff -- src/foo.py            # конкретный файл(ы)
```

Если `git diff` и `git diff HEAD` оба пусты и нет git-репозитория или
изменений — откатись на файлы, явно названные пользователем или недавно
созданные/изменённые в этой сессии. Если изменённого код действительно нет —
скажи об этом и остановись: упрощать нечего.

Захвати полный текст diff. Отметь размер: если он очень большой (скажем, >2000
изменённых строк), предупреди пользователя, что четыре субагента с полным diff
будут дороги по токенам, и предложи сузить область (по директории, по коммиту)
до продолжения.

### Фаза 2 — Запусти четырёх ревьюеров параллельно

Используй agents.run **пакетом** — все четыре задачи одним вызовом, чтобы они
работали конкурентно. Четыре — правильный веер для этого паттерна.

**Делегирование недоступно?** Если agents.run в этом контексте вызвать нельзя
(ты листовой субагент, делегирование отключено или бюджет исчерпан) — НЕ
пропускай ревью и не роняй углы. Пройди все четыре угла сам, последовательно,
в этом контексте — те же стандарты поиска, тот же формат находок. И ясно
скажи в финальном резюме, что это был однопроходный inline-ревью, а не
параллельный веер, чтобы пользователь знал, что реально выполнялось.

Дай **каждому** ревьюеру **полный diff** (не фрагменты — межфайловые проблемы
прячутся в щелях) плюс абсолютный путь к репозиторию, чтобы искать шире. Каждый
ревьюер должен уметь запускать `git`, читать файлы и искать по коду
(files.read / files.search / grep).

Скажи каждому ревьюеру:

- Искать доказательства в существующей кодовой базе (не рассуждать по одному
  diff).
- **Применять «забор Честертона»:** прежде чем помечать что-то на удаление,
  прогони `git blame` по строке, чтобы понять, зачем она существует. Если
  исходное назначение определить нельзя — помечай `confidence: low`, не гадай.
- Докладывать находки структурировано, с конкретной ценой, уверенностью и
  риском:
  ```
  file:line → проблема → цена (что дублируется/тратится/сложнее поддерживать) → предлагаемый фикс | confidence: high/medium/low | risk: SAFE/CAREFUL/RISKY
  ```
  Поле **цена** заставляет каждую находку себя оправдать — находка, не
  способная сформулировать, чего проблема стоит, скорее всего придирка.
  - **SAFE** = доказано, что не влияет на поведение (неиспользуемые импорты,
    закомментированный код, сквозные обёртки). Применяй автоматически.
  - **CAREFUL** = улучшает без смены семантики (переименование локальной
    переменной, сплющивание вложенного тернарника, выделение хелпера).
    Применяй с проверкой тестами.
  - **RISKY** = может менять поведение или ломать публичные контракты
    (перестройка N+1, переименование публичного API, смена жизненного цикла
    памяти). Помечай для ревью человеком — НЕ применяй автоматически.
- Пропускай придирки и чисто стилистический шум. Помечай только то, что
  существенно улучшает код.

Передай эти четыре задачи (выкинь те, что исключены фокусом пользователя):

**Ревьюер 1 — Переиспользование кода**
> Проверь этот diff на код, дублирующий функциональность, уже существующую в
> кодовой базе. Ищи в утилитных модулях, общих хелперах и соседних файлах
> (files.search / grep) существующие функции, константы или паттерны, которые
> новый код мог бы вызывать вместо переизобретения. Помечай: новые функции,
> дублирующие существующие; рукодельную логику, которую уже делает
> существующая утилита (ручная работа со строками/путями, свои проверки env,
> ad-hoc type guards, переизобретённый парсинг). Для каждой — назови
> существующую вещь и где она живёт.

**Ревьюер 2 — Качество кода**
> Проверь этот diff на проблемы качества. Ищи: избыточное состояние (значения,
> дублирующие или выводимые из существующего состояния; ненужные кеши);
> разрастание параметров (новые параметры, приболченные туда, где функцию
> стоило перестроить); копипаст-с-вариациями (почти дублирующие блоки, которым
> нужна общая абстракция); протекающие абстракции (экспозиция внутренностей,
> слом существующей границы инкапсуляции); stringly-typed код (сырые строки
> там, где есть константа/enum/реестр — проверь канонические реестры до
> пометки); глубоко вложенные условия (цепочки тернарников, 3+-уровневые
> пирамиды if/else — сплющи стражами, ранними return или таблицей поиска);
> паттерны ИИ-слопа (лишние комментарии, пересказывающие очевидный код, вроде
> `// increment counter` над `count++`; ненужные защитные null-проверки на уже
> валидированных входах; `as any`-касты, обходящие систему типов; паттерны,
> несогласованные с остальным файлом). Для каждой — конкретный рефакторинг.

**Ревьюер 3 — Эффективность**
> Проверь этот diff на проблемы эффективности. Ищи: ненужную работу
> (избыточные вычисления, повторные чтения файлов, дублирующие вызовы API,
> паттерны N+1); упущенный параллелизм (независимые операции выполняются
> последовательно); раздутие горячего пути (тяжёлая/блокирующая работа на
> старте или на per-request путях); антипаттерны TOCTOU (предварительные
> проверки существования перед операцией вместо выполнения операции и
> обработки ошибки); проблемы памяти (неограниченный рост, пропущенная очистка,
> утечки слушателей/дескрипторов; долгоживущие колбэки или объекты-замыкания,
> захватывающие всю охватывающую область — всё захваченное живёт, пока живёт
> объект, поэтому предпочитай маленький класс или структуру с явными полями,
> копирующую только нужное); слишком широкие чтения (загрузка целых файлов,
> когда хватило бы среза); тихие сбои (пустые catch-блоки, игнорируемые
> возвраты ошибок, `except: pass`, `.catch(() => {})` без обработки, дыры в
> распространении ошибок — они прячут баги и должны как минимум логировать
> перед проглатыванием). Для каждой — конкретный фикс и почему быстрее или
> безопаснее.

**Ревьюер 4 — Глубина (altitude)**
> Проверь этот diff на изменения, реализованные на неверной глубине, —
> заплатки, наложенные поверх общей инфраструктуры вместо правок самой
> инфраструктуры. Признаки слишком мелкой правки: особый случай, добавленный в
> общий код-путь ради одного вызывающего (ветка `if (caller == X)`, проверка
> типа, лазейка магического значения); симптом залатан в месте вызова, пока
> соседние места вызова несут тот же изъян; обходной путь, сложенный на более
> ранний обходной путь; обёртка, добавленная, чтобы не трогать то, что
> действительно требует изменения; конфигурация или флаги, введённые, чтобы
> обойти сломанный дефолт вместо починки дефолта. Для каждой — определи
> лежащий в основе механизм, которого изменение избегает, и опиши более
> глубокий фикс — обобщи общий путь, почини корневой дефолт или почини весь
> класс багов — и честно отметь, когда более глубокий фикс достаточно велик,
> чтобы быть отдельной задачей, а не частью этой чистки. Сначала прочитай
> окружающий код и `git blame`: то, что выглядит заплаткой, иногда —
> намеренная граница (compat-шимы, поэтапные миграции, изоляция vendored-кода).
> Их не помечай.

### Фаза 3 — Агрегируй и применяй

Дождись всех четырёх (пакетный режим возвращает их вместе).

1. **Слей** находки в один список, дедуплицируя пересечения — когда две находки
   целятся в одну строку или один механизм, сверни в одну.
2. **Отбрось ложные срабатывания** — у тебя больше всего контекста; не обязан
   спорить с ревьюером, просто молча выкидывай слабые или неверные
   предложения.
3. **Разреши конфликты.** Ревьюеры могут расходиться (Ревьюер 1: «используй
   существующий util X»; Ревьюер 3: «X медленный, инлайнь»). Порядок
   разрешения по умолчанию: **корректность > заявленный фокус пользователя >
   читаемость/переиспользование > микро-перф.** Не применяй перф-«фикс»,
   вредящий ясности, если путь не по-настоящему горячий. Когда два предложения
   взаимоисключающи и оба защитимы — выбирай то, что трогает меньше кода, и
   отметь альтернативу.
4. **Применяй в порядке уровней риска:**
   - **SAFE первыми** (автоприменение): неиспользуемые импорты,
     закомментированный код, сквозные обёртки, избыточные типовые утверждения.
     Прогони тесты после.
   - **CAREFUL следующими** (применяй с верификацией, по одному файлу):
     переименование локалок, сплющивание тернарников, выделение хелперов,
     консолидация дублей. Прогоняй тесты после каждого файла. Откатывай то,
     что ломает.
   - **RISKY последними** (помечай для ревью — НЕ автоприменяй): перестройка
     N+1, изменения публичного API, фиксы конкурентности, изменения обработки
     ошибок. Представляй каждую с описанием риска и статусом покрытия тестами.
     Находки глубины обычно попадают сюда — углубление фикса значит трогать
     общую инфраструктуру, поэтому представь глубокий фикс и дай пользователю
     решить, делать сейчас или отдельной задачей.
   Если пользователь выбрал сухой прогон — представь все три уровня и не
   применяй ничего.
5. **Проверь**, что ничего не сломал: прогони точечные тесты проекта по
   затронутым файлам (не весь сьют) и перезапусти линтер/проверку типов,
   которые использует репозиторий. Если фикс ломает тест — откати именно этот
   фикс и доложи.
6. **Резюмируй**, что изменил: короткий список применённых фиксов, сгруппирован
   по категории ревьюера и уровню риска, плюс находки, которые сознательно
   пропустил, и почему. Если работал inline (без делегирования) — скажи это
   здесь.

## Ловушки

- **Не расширяй веер шире 4.** Больше ревьюеров — больше стоимость и больше
  конфликтующих предложений для разрешения, а не лучшее покрытие. Четыре
  категории покрывают пространство.
- **Давай ВЕСЬ diff каждому ревьюеру.** Нарезка diff между ревьюерами ломает
  дизайн — межфайловые дубли и N+1 видны только с полной картиной.
- **Ревьюеры ищут, не гадают.** Находка о переиспользовании без указателя на
  существующую утилиту («наверное, есть хелпер») — шум. Требуй доказательства
  `file:line`; выкидывай находки без них.
- **Применять ≠ переписывать.** Это чистка недавних изменений пользователя, а
  не лицензия на рефакторинг всего модуля. Держи правки в рамках того, что
  тронул diff, плюс минимальное окружение, необходимое фиксу. Находки глубины
  — исключение, подтверждающее правило: когда правильный фикс глубже diff,
  ПОМЕТЬ его — не перестраивай общий механизм внутри прохода чистки
  единолично.
- **Не съезжай в охоту на баги.** Если ревьюер вскрыл настоящий баг
  корректности — доложи заметно, но отдельной пометкой «найден баг», а не
  свёрнутой в фиксы чистки. Ревью корректности — другой проход с другими
  стандартами верификации.
- **Уважай конвенции проекта.** Если в репозитории есть AGENTS.md / CLAUDE.md
  или конфиг линтера — встрой эти правила в промпты ревьюеров, чтобы
  предложения соответствовали домашнему стилю, а не боролись с ним.
- **Большие diff раздувают контекст.** Если diff огромный — сузь его до
  делегирования: четыре субагента с diff на 5000 строк дороги и могут
  обрезаться.
- **Чрезмерное доверие инструментам мёртвого кода.** `knip`, `ts-prune`,
  `depcheck` помечают экспорты, которые ИСПОЛЬЗУЮТСЯ динамически (строковые
  импорты, рефлексия). Всегда grep по имени символа перед удалением — чистый
  отчёт инструмента не доказательство.
- **Переименование без проверки публичных контрактов.** Имена экспортов, пути
  API-роутов, имена колонок БД и ключи конфига — контракты: даже плохое имя
  при переименовании ломает потребителей. Помечай изменения публичных
  контрактов как RISKY; никогда не переименовывай их автоматически.
- **Удаление «ненужной» обработки ошибок.** Пустой catch или игнорируемая
  ошибка могут быть намеренными — ошибка ожидаема и безвредна в этом контексте.
  Помечай, не удаляй; пусть решает человек.
- **Не каждый особый случай — заплатка.** Compat-шимы, поэтапные миграции и
  изоляционные слои вокруг vendored-кода выглядят как нарушения глубины, но
  являются намеренным дизайном. Проверяй `git blame` и окружающие комментарии
  до пометки; когда намерение неясно — `confidence: low`.

## Связанное

`code-review-ru` / `security-audit-ru` — ревью корректности и безопасности
(охота на баги). Этот скилл — отдельный проход чистки после факта.

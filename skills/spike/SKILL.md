# Спайк (spike)

Используй, когда пользователь хочет **прощупать идею** до серьёзной сборки —
проверить осуществимость, сравнить подходы, вскрыть неизвестные, которые
никакое чтение доков не ответит. Спайки одноразовые по замыслу. Выбрасывай их,
когда они отдали свой долг.

Загружай, когда звучит что-то вроде «дай попробую», «хочу проверить, сработает
ли X», «сделай спайк», «прежде чем браться за Y», «быстрый прототип Z»,
«а это вообще возможно?», «сравни A и B».

## Когда НЕ использовать

- Ответ находится в доках или чтении кода — просто исследуй, не строй.
- Работа — продакшн-путь — используй скилл `plan`.
- Идея уже проверена — сразу к реализации.

## Базовый метод

Независимо от масштаба, каждый спайк следует циклу:

```
декомпозиция  →  исследование  →  сборка  →  вердикт
   ↑_______________________________________________↓
                итерации по находкам
```

### 1. Декомпозиция

Разбей идею пользователя на **2–5 независимых вопросов осуществимости**. Каждый
вопрос — один спайк. Представь их таблицей в рамке Given/When/Then:

| # | Спайк | Что проверяет (Given/When/Then) | Риск |
|---|-------|--------------------------------|------|
| 001 | websocket-streaming | Given WS-соединение, when LLM стримит токены, then клиент получает чанки < 100ms | Высокий |
| 002a | pdf-parse-pdfjs | Given многостраничный PDF, when парсится pdfjs, then извлекается структурированный текст | Средний |
| 002b | pdf-parse-camelot | Given многостраничный PDF, when парсится camelot, then извлекается структурированный текст | Средний |

**Типы спайков:**
- **standard** — один подход отвечает на один вопрос.
- **comparison** — один вопрос, разные подходы (общий номер, суффикс
  `a`/`b`/`c`).

**Хорошие вопросы спайка:** конкретная осуществимость с наблюдаемым выводом.
**Плохие:** слишком широкие, без наблюдаемого вывода, или просто «почитай доки
про X».

**Упорядочивай по риску.** Спайк, наиболее вероятно убивающий идею, идёт
первым. Нет смысла прототипировать лёгкое, если трудное не работает.

**Пропускай декомпозицию**, только если пользователь точно знает, что спайкать,
и прямо говорит об этом. Тогда бери его идею как один спайк.

### 2. Согласование (для мультиспайковых идей)

Покажи таблицу спайков. Спроси: «Строим все в этом порядке или корректируем?»
Дай пользователю выкинуть, переупорядочить, переформулировать — до написания
кода.

### 3. Исследование (на спайк, до сборки)

Спайки не лишены исследования — исследуешь ровно столько, чтобы выбрать
правильный подход, потом строишь. На спайк:

1. **Бриф.** 2–3 предложения: что это за спайк, зачем, ключевой риск.
2. **Вскрой конкурирующие подходы**, если выбор реален:

   | Подход | Инструмент/библиотека | Плюсы | Минусы | Статус |
   |--------|----------------------|-------|--------|--------|
   | ... | ... | ... | ... | maintained / abandoned / beta |

3. **Выбери один.** Объясни почему. Если 2+ правдоподобны — строй быстрые
   варианты внутри спайка.
4. **Пропускай исследование** для чистой логики без внешних зависимостей.

Инструменты для исследования:

- `web.search` — найти кандидатов (например, "python websocket streaming libraries 2025")
- `http.fetch` — прочитать сами доки по URL
- `terminal.exec` — проверить, что уже установлено: `pip show websockets | grep Version`

Для библиотек без страниц документации — клонируй и читай `README.md` /
`examples/` через files.read.

### 4. Сборка

Одна директория на спайк. Автономно.

```
spikes/
├── 001-websocket-streaming/
│   ├── README.md
│   └── main.py
├── 002a-pdf-parse-pdfjs/
│   ├── README.md
│   └── parse.js
└── 002b-pdf-parse-camelot/
    ├── README.md
    └── parse.py
```

**Приоритет — тому, с чем пользователь может взаимодействовать.** Спайки
проваливаются, когда единственный вывод — строчка в логе «работает». Порядок
предпочтения:

1. Запускаемый CLI, принимающий вход и печатающий наблюдаемый вывод.
2. Минимальная HTML-страница, демонстрирующая поведение.
3. Маленький веб-сервер с одним эндпоинтом.
4. Юнит-тест, упражняющий вопрос узнаваемыми проверками.

**Глубина важнее скорости.** Никогда не объявляй «работает» после одного
прогона happy path. Проверяй граничные случаи. Следуй за неожиданными
находками. Вердикту можно верить, только если исследование было честным.

**Избегай**, если спайк этого явно не требует: сложного управления пакетами,
сборщиков/бандлеров, Docker, env-файлов, систем конфигурации. Хардкодь всё —
это спайк.

**Типовая последовательность для одного спайка:**

```
terminal: mkdir -p spikes/001-websocket-streaming
files.write: spikes/001-websocket-streaming/README.md
files.write: spikes/001-websocket-streaming/main.py
terminal: cd spikes/001-websocket-streaming && python main.py
# Наблюдай вывод, итерируй.
```

**Параллельные сравнительные спайки (002a / 002b) — делегируй.** Когда два
подхода могут идти параллельно и оба требуют настоящей инженерии (не
10-строчных прототипов), запусти их через agents.run пакетом — по задаче на
каждый вариант. Каждый субагент возвращает свой вердикт; итоговое сравнение
пишешь ты.

### 5. Вердикт

`README.md` каждого спайка завершается:

```markdown
## Verdict: VALIDATED | PARTIAL | INVALIDATED

### Что сработало
- ...

### Что не сработало
- ...

### Неожиданности
- ...

### Рекомендация для реальной сборки
- ...
```

**VALIDATED** — на основной вопрос ответ «да», с доказательствами.
**PARTIAL** — работает при ограничениях X, Y, Z — задокументируй их.
**INVALIDATED** — не работает, по такой-то причине. Это успешный спайк.

## Сравнительные спайки

Когда два подхода отвечают на один вопрос (002a / 002b), строй их **подряд**,
затем делай очное сравнение:

```markdown
## Очное сравнение: pdfjs vs camelot

| Измерение | pdfjs (002a) | camelot (002b) |
|-----------|--------------|----------------|
| Качество извлечения | 9/10 структурировано | 7/10 только таблицы |
| Сложность setup | npm install, 1 строка | pip + ghostscript |
| Производительность на 100-стр. PDF | 3s | 18s |
| Повёрнутый текст | нет | да |

**Победитель:** pdfjs для нашего случая. Camelot — если позже понадобится
извлечение «таблицы в первую очередь».
```

## Режим фронтира (что спайкать дальше)

Если спайки уже есть и пользователь спрашивает «что дальше?» — пройди по
существующим директориям и ищи:

- **Риски интеграции** — два проверенных спайка трогают один ресурс, но
  тестировались независимо.
- **Передачи данных** — вывод спайка A предполагался совместимым со входом
  спайка B; никогда не доказано.
- **Дыры в видении** — возможности предполагались, но не проверены.
- **Альтернативные подходы** — другие углы для PARTIAL или INVALIDATED.

Предложи 2–4 кандидата в формате Given/When/Then. Пусть пользователь выберет.

## Результат

- Создай `spikes/` в корне репозитория.
- Одна директория на спайк: `NNN-descriptive-name/`.
- `README.md` на спайк фиксирует вопрос, подход, результаты, вердикт.
- Код держи одноразовым — спайк, который 2 дня «чистят для прода», был плохим
  спайком.

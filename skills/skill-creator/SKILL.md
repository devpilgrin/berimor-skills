# Skill Creator

Скилл для создания новых скиллов и их итеративного улучшения.

На высоком уровне процесс создания скилла выглядит так:

- Реши, что скилл должен делать и примерно как
- Напиши черновик скилла
- Создай несколько тестовых промптов и прогони на них claude-with-access-to-the-skill
- Помоги пользователю оценить результаты качественно и количественно
  - Пока прогоны идут в фоне, набросай количественные evals, если их нет (если есть, можешь использовать как есть или изменить, если чувствуешь, что что-то нужно поправить). Затем объясни их пользователю (или, если они уже существовали, объясни существующие)
  - Используй скрипт `eval-viewer/generate_review.py`, чтобы показать пользователю результаты, а также дай ему посмотреть количественные метрики
- Перепиши скилл на основе обратной связи от пользователя по результатам (а также если в количественных бенчмарках обнаружились явные недостатки)
- Повторяй, пока не будешь удовлетворён
- Расширь набор тестов и попробуй снова в большем масштабе

Твоя задача при использовании этого скилла — понять, на каком этапе процесса находится пользователь, и включиться, помогая ему продвигаться по этим стадиям. Например, пользователь может сказать: «Я хочу сделать скилл для X». Ты можешь помочь уточнить, что он имеет в виду, написать черновик, написать тест-кейсы, выяснить, как он хочет оценивать, прогнать все промпты и повторить.

С другой стороны, возможно, у него уже есть черновик скилла. В этом случае можно сразу перейти к части цикла с eval/итерациями.

Разумеется, всегда будь гибким: если пользователь говорит «Мне не нужно прогонять кучу оценок, просто работай со мной на вайбе», делай так.

Затем, когда скилл готов (но порядок опять же гибкий), можно также запустить улучшатель описания скилла — для него у нас есть отдельный скрипт — чтобы оптимизировать срабатывание скилла.

Договорились? Договорились.

## Общение с пользователем

Skill creator могут использовать люди с самым разным уровнем знакомства с программистским жаргоном. Если ты не слышал (а откуда бы — это началось совсем недавно), сейчас есть тренд: мощь Claude вдохновляет сантехников открывать терминалы, а родителей и бабушек с дедушками — гуглить «how to install npm». С другой стороны, основная масса пользователей, вероятно, довольно компьютерно грамотна.

Так что обращай внимание на контекстные сигналы, чтобы понять, как формулировать общение! В случае по умолчанию, чтобы дать представление:

- «evaluation» и «benchmark» — на грани, но допустимо
- для «JSON» и «assertion» нужны серьёзные сигналы от пользователя, что он знает эти термины, прежде чем использовать их без объяснений

Нормально кратко объяснять термины, если сомневаешься, и не стесняйся уточнять термины коротким определением, если не уверен, что пользователь поймёт.

## Создание скилла

### Зафиксируй намерение

Начни с понимания намерения пользователя. Текущий разговор может уже содержать рабочий процесс, который пользователь хочет зафиксировать (например, он говорит «преврати это в скилл»). Если так, сначала извлеки ответы из истории разговора — использованные инструменты, последовательность шагов, правки пользователя, наблюдаемые форматы ввода/вывода. Пользователю может понадобиться заполнить пробелы, и он должен подтвердить перед переходом к следующему шагу.

1. Что этот скилл должен позволить Claude делать?
2. Когда этот скилл должен срабатывать? (какие фразы/контексты пользователя)
3. Какой ожидаемый формат вывода?
4. Стоит ли настроить тест-кейсы для проверки работы скилла? Скиллы с объективно проверяемым выводом (преобразования файлов, извлечение данных, генерация кода, фиксированные шаги рабочего процесса) выигрывают от тест-кейсов. Скиллы с субъективным выводом (стиль письма, искусство) часто в них не нуждаются. Предложи подходящее значение по умолчанию исходя из типа скилла, но решение пусть принимает пользователь.

### Интервью и исследование

Проактивно задавай вопросы о граничных случаях, форматах ввода/вывода, примерах файлов, критериях успеха и зависимостях. Не пиши тестовые промпты, пока эта часть не устаканится.

Проверь доступные MCP — если они полезны для исследования (поиск документации, поиск похожих скиллов, поиск лучших практик), исследуй параллельно через субагентов, если они доступны, иначе инлайн. Приходи подготовленным с контекстом, чтобы снизить нагрузку на пользователя.

### Напиши SKILL.md

На основе интервью с пользователем заполни эти компоненты:

- **name**: Идентификатор скилла
- **description**: Когда срабатывать, что делает. Это основной механизм срабатывания — включи и то, что скилл делает, И конкретные контексты, когда его использовать. Вся информация «когда использовать» идёт сюда, а не в тело. Учти: сейчас у Claude есть тенденция «недосрабатывать» скиллы — не использовать их, когда они были бы полезны. Чтобы это компенсировать, делай описания скиллов немного «настойчивыми». Например, вместо «How to build a simple fast dashboard to display internal Anthropic data.» можно написать «How to build a simple fast dashboard to display internal Anthropic data. Make sure to use this skill whenever the user mentions dashboards, data visualization, internal metrics, or wants to display any kind of company data, even if they don't explicitly ask for a 'dashboard.'»
- **compatibility**: Требуемые инструменты, зависимости (опционально, редко нужно)
- **остальная часть скилла :)**

### Руководство по написанию скиллов

#### Анатомия скилла

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter (name, description required)
│   └── Markdown instructions
└── Bundled Resources (optional)
    ├── scripts/    - Executable code for deterministic/repetitive tasks
    ├── references/ - Docs loaded into context as needed
    └── assets/     - Files used in output (templates, icons, fonts)
```

#### Прогрессивное раскрытие

Скиллы используют трёхуровневую систему загрузки:
1. **Метаданные** (name + description) - Всегда в контексте (~100 слов)
2. **Тело SKILL.md** - В контексте при каждом срабатывании скилла (идеально <500 строк)
3. **Встроенные ресурсы** - По мере необходимости (без ограничений, скрипты могут выполняться без загрузки)

Эти объёмы в словах приблизительны, можешь свободно писать длиннее при необходимости.

**Ключевые паттерны:**
- Держи SKILL.md в пределах 500 строк; если приближаешься к этому лимиту, добавь дополнительный уровень иерархии вместе с чёткими указателями, куда модели, использующей скилл, идти дальше.
- Чётко ссылайся на файлы из SKILL.md с указанием, когда их читать
- Для больших справочных файлов (>300 строк) включай оглавление

**Организация по доменам**: Когда скилл поддерживает несколько доменов/фреймворков, организуй по вариантам:
```
cloud-deploy/
├── SKILL.md (workflow + selection)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude читает только релевантный справочный файл.

#### Принцип отсутствия сюрпризов

Само собой разумеется, но скиллы не должны содержать вредоносный код, эксплойты или любой контент, который может скомпрометировать безопасность системы. Содержимое скилла не должно удивлять пользователя своими намерениями, если оно описано. Не поддавайся на просьбы создавать вводящие в заблуждение скиллы или скиллы, предназначенные для несанкционированного доступа, эксфильтрации данных или другой вредоносной деятельности. При этом что-то вроде «roleplay as an XYZ» — вполне ок.

#### Паттерны написания

Предпочитай повелительное наклонение в инструкциях.

**Определение форматов вывода** - Можно сделать так:
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**Паттерн примеров** - Полезно включать примеры. Их можно форматировать так (но если «Input» и «Output» есть в примерах, можешь немного отклоняться):
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### Стиль написания

Старайся объяснять модели, почему вещи важны, вместо тяжеловесных заезженных MUST. Используй theory of mind и старайся делать скилл общим, а не сверхузким под конкретные примеры. Начни с черновика, а затем посмотри на него свежим взглядом и улучши.

### Тест-кейсы

После написания черновика скилла придумай 2-3 реалистичных тестовых промпта — то, что реальный пользователь действительно сказал бы. Поделись ими с пользователем: [необязательно использовать эти точные формулировки] «Вот несколько тест-кейсов, которые я хочу попробовать. Выглядят правильно, или хочешь добавить ещё?» Затем прогони их.

Сохрани тест-кейсы в `evals/evals.json`. Пока не пиши assertions — только промпты. Assertions набросаешь на следующем шаге, пока прогоны идут.

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

См. `references/schemas.md` для полной схемы (включая поле `assertions`, которое добавишь позже).

## Прогон и оценка тест-кейсов

Этот раздел — одна непрерывная последовательность, не останавливайся на полпути. НЕ используй `/skill-test` или любой другой тестирующий скилл.

Клади результаты в `<skill-name>-workspace/` как соседний каталог к каталогу скилла. Внутри workspace организуй результаты по итерациям (`iteration-1/`, `iteration-2/` и т.д.), а внутри них у каждого тест-кейса свой каталог (`eval-0/`, `eval-1/` и т.д.). Не создавай всё это заранее — создавай каталоги по ходу дела.

### Шаг 1: Запусти все прогоны (with-skill И baseline) в одном ходе

Для каждого тест-кейса запусти двух субагентов в одном ходе — одного со скиллом, одного без. Это важно: не запускай сначала прогоны with-skill, а потом возвращайся за baseline. Запускай всё сразу, чтобы всё завершилось примерно одновременно.

**Прогон with-skill:**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Прогон baseline** (тот же промпт, но baseline зависит от контекста):
- **Создание нового скилла**: вообще без скилла. Тот же промпт, без пути к скиллу, сохранить в `without_skill/outputs/`.
- **Улучшение существующего скилла**: старая версия. Перед редактированием сделай снапшот скилла (`cp -r <skill-path> <workspace>/skill-snapshot/`), затем направь baseline-субагента на снапшот. Сохранить в `old_skill/outputs/`.

Напиши `eval_metadata.json` для каждого тест-кейса (assertions пока могут быть пустыми). Дай каждому eval описательное имя на основе того, что он тестирует, — не просто «eval-0». Используй это имя и для каталога. Если в этой итерации используются новые или изменённые eval-промпты, создай эти файлы для каждого нового каталога eval — не предполагай, что они переносятся из предыдущих итераций.

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### Шаг 2: Пока прогоны идут, набросай assertions

Не просто жди завершения прогонов — используй это время продуктивно. Набросай количественные assertions для каждого тест-кейса и объясни их пользователю. Если assertions уже существуют в `evals/evals.json`, просмотри их и объясни, что они проверяют.

Хорошие assertions объективно проверяемы и имеют описательные имена — они должны ясно читаться в просмотрщике бенчмарков, чтобы человек, мельком глянув на результаты, сразу понял, что проверяет каждый. Субъективные скиллы (стиль письма, качество дизайна) лучше оценивать качественно — не навязывай assertions вещам, требующим человеческого суждения.

Обнови файлы `eval_metadata.json` и `evals/evals.json` с assertions после их подготовки. Также объясни пользователю, что он увидит в просмотрщике — и качественные выводы, и количественный бенчмарк.

### Шаг 3: По мере завершения прогонов фиксируй данные о времени

Когда каждая задача субагента завершается, ты получаешь уведомление, содержащее `total_tokens` и `duration_ms`. Немедленно сохрани эти данные в `timing.json` в каталоге прогона:

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

Это единственная возможность зафиксировать эти данные — они приходят через уведомление о задаче и больше нигде не сохраняются. Обрабатывай каждое уведомление по мере поступления, а не пытайся собрать их пакетом.

### Шаг 4: Оцени, агрегируй и запусти просмотрщик

Когда все прогоны завершены:

1. **Оцени каждый прогон** — запусти субагента-оценщика (или оцени инлайн), который читает `agents/grader.md` и оценивает каждый assertion по выводам. Сохрани результаты в `grading.json` в каждом каталоге прогона. Массив expectations в grading.json должен использовать поля `text`, `passed` и `evidence` (не `name`/`met`/`details` или другие варианты) — просмотрщик зависит от этих точных имён полей. Для assertions, которые можно проверить программно, напиши и запусти скрипт вместо оценки на глаз — скрипты быстрее, надёжнее и могут переиспользоваться между итерациями.

2. **Агрегируй в бенчмарк** — запусти скрипт агрегации из каталога skill-creator:
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   Это создаёт `benchmark.json` и `benchmark.md` с pass_rate, временем и токенами для каждой конфигурации, со средним ± стандартным отклонением и дельтой. Если генерируешь benchmark.json вручную, см. `references/schemas.md` для точной схемы, которую ожидает просмотрщик.
Каждую версию with_skill ставь перед её baseline-аналогом.

3. **Сделай аналитический проход** — прочитай данные бенчмарка и выяви паттерны, которые агрегированная статистика может скрывать. См. `agents/analyzer.md` (раздел «Analyzing Benchmark Results») о том, что искать — например, assertions, которые всегда проходят независимо от скилла (недискриминирующие), evals с высокой дисперсией (возможно, нестабильные) и компромиссы по времени/токенам.

4. **Запусти просмотрщик** с качественными выводами и количественными данными:
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   Для итерации 2+ также передай `--previous-workspace <workspace>/iteration-<N-1>`.

   **Cowork / headless-окружения:** Если `webbrowser.open()` недоступен или в окружении нет дисплея, используй `--static <output_path>`, чтобы записать автономный HTML-файл вместо запуска сервера. Обратная связь будет скачана как файл `feedback.json`, когда пользователь нажмёт «Submit All Reviews». После скачивания скопируй `feedback.json` в каталог workspace, чтобы следующая итерация его подхватила.

Примечание: используй generate_review.py для создания просмотрщика; писать собственный HTML не нужно.

5. **Скажи пользователю** что-то вроде: «Я открыл результаты в твоём браузере. Там две вкладки — 'Outputs' позволяет пролистать каждый тест-кейс и оставить обратную связь, 'Benchmark' показывает количественное сравнение. Когда закончишь, вернись сюда и скажи мне.»

### Что пользователь видит в просмотрщике

Вкладка «Outputs» показывает по одному тест-кейсу за раз:
- **Prompt**: задача, которая была дана
- **Output**: файлы, которые произвёл скилл, отрендеренные инлайн где возможно
- **Previous Output** (итерация 2+): свёрнутая секция с выводом прошлой итерации
- **Formal Grades** (если запускалась оценка): свёрнутая секция с прохождением/провалом assertions
- **Feedback**: текстовое поле с автосохранением по мере ввода
- **Previous Feedback** (итерация 2+): их комментарии с прошлого раза, показанные под текстовым полем

Вкладка «Benchmark» показывает сводку статистики: pass rates, время и использование токенов для каждой конфигурации, с разбивкой по eval и аналитическими наблюдениями.

Навигация — через кнопки prev/next или клавиши-стрелки. По завершении пользователь нажимает «Submit All Reviews», что сохраняет всю обратную связь в `feedback.json`.

### Шаг 5: Прочитай обратную связь

Когда пользователь скажет, что закончил, прочитай `feedback.json`:

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

Пустая обратная связь означает, что пользователь счёл результат нормальным. Сфокусируй улучшения на тест-кейсах, где у пользователя были конкретные претензии.

Останови сервер просмотрщика, когда закончишь с ним:

```bash
kill $VIEWER_PID 2>/dev/null
```

## Улучшение скилла

Это сердце цикла. Ты прогнал тест-кейсы, пользователь просмотрел результаты, и теперь нужно сделать скилл лучше на основе его обратной связи.

### Как думать об улучшениях

1. **Обобщай обратную связь.** Главная картина здесь такова: мы пытаемся создавать скиллы, которые можно использовать миллион раз (может, буквально, может, даже больше — кто знает) на множестве разных промптов. Здесь вы с пользователем итерируете снова и снова лишь на нескольких примерах, потому что это помогает двигаться быстрее. Пользователь знает эти примеры вдоль и поперёк, и ему быстро оценивать новые выводы. Но если скилл, который вы вместе разрабатываете, работает только на этих примерах, он бесполезен. Вместо того чтобы вносить придирчивые оверфитнутые правки или удушающе ограничительные MUST, если есть какая-то упрямая проблема, можно попробовать разветвиться и использовать другие метафоры или рекомендовать другие паттерны работы. Это относительно дёшево попробовать, и, может быть, ты попадёшь в нечто отличное.

2. **Держи промпт компактным.** Убирай вещи, которые не окупают своё присутствие. Обязательно читай транскрипты, а не только финальные выводы — если похоже, что скилл заставляет модель тратить кучу времени на непродуктивные действия, можно попробовать избавиться от частей скилла, которые заставляют её так делать, и посмотреть, что получится.

3. **Объясняй «почему».** Очень старайся объяснять **почему** за всем, о чём ты просишь модель. Сегодняшние LLM *умные*. У них хорошая theory of mind, и с хорошим harness они могут выходить за рамки механических инструкций и действительно добиваться результата. Даже если обратная связь от пользователя лаконична или раздражена, постарайся действительно понять задачу и почему пользователь пишет то, что пишет, и что именно он написал, а затем передай это понимание в инструкции. Если ты обнаруживаешь, что пишешь ALWAYS или NEVER капсом или используешь сверхжёсткие структуры, это жёлтый флаг — по возможности переформулируй и объясни обоснование, чтобы модель понимала, почему то, о чём ты просишь, важно. Это более человечный, мощный и эффективный подход.

4. **Ищи повторяющуюся работу между тест-кейсами.** Читай транскрипты тестовых прогонов и замечай, писали ли субагенты независимо друг от друга похожие вспомогательные скрипты или использовали один и тот же многошаговый подход к чему-то. Если все 3 тест-кейса привели к тому, что субагент написал `create_docx.py` или `build_chart.py`, это сильный сигнал, что скилл должен поставляться с этим скриптом. Напиши его один раз, положи в `scripts/` и скажи скиллу его использовать. Это избавляет каждый будущий вызов от изобретения колеса.

Эта задача действительно важна (мы пытаемся создавать миллиарды в год экономической ценности!), и время твоих размышлений не является узким местом; не торопись и действительно обмозгуй всё. Я бы посоветовал написать черновик ревизии, а затем взглянуть на него заново и внести улучшения. Действительно постарайся залезть в голову пользователя и понять, что он хочет и в чём нуждается.

### Цикл итерации

После улучшения скилла:

1. Примени свои улучшения к скиллу
2. Перезапусти все тест-кейсы в новый каталог `iteration-<N+1>/`, включая baseline-прогоны. Если создаёшь новый скилл, baseline всегда `without_skill` (без скилла) — это остаётся неизменным между итерациями. Если улучшаешь существующий скилл, рассуди сам, что имеет смысл в качестве baseline: оригинальная версия, с которой пришёл пользователь, или предыдущая итерация.
3. Запусти просмотрщик с `--previous-workspace`, указывающим на предыдущую итерацию
4. Дождись, пока пользователь просмотрит и скажет, что закончил
5. Прочитай новую обратную связь, улучши снова, повтори

Продолжай, пока:
- Пользователь не скажет, что доволен
- Обратная связь не будет вся пустой (всё выглядит хорошо)
- Ты не перестанешь добиваться значимого прогресса

## Продвинутое: слепое сравнение

Для ситуаций, когда нужно более строгое сравнение двух версий скилла (например, пользователь спрашивает «новая версия действительно лучше?»), есть система слепого сравнения. Прочитай `agents/comparator.md` и `agents/analyzer.md` для деталей. Основная идея: дать два вывода независимому агенту, не говоря, какой есть какой, и позволить ему судить качество. Затем проанализировать, почему победитель победил.

Это опционально, требует субагентов, и большинству пользователей не понадобится. Обычно достаточно цикла человеческого ревью.

## Оптимизация описания

Поле description во frontmatter SKILL.md — основной механизм, определяющий, вызовет ли Claude скилл. После создания или улучшения скилла предложи оптимизировать описание для лучшей точности срабатывания.

### Шаг 1: Сгенерируй триггерные eval-запросы

Создай 20 eval-запросов — смесь should-trigger и should-not-trigger. Сохрани как JSON:

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

Запросы должны быть реалистичными — такими, которые пользователь Claude Code или Claude.ai действительно напечатал бы. Не абстрактные просьбы, а конкретные и специфичные запросы с хорошей детализацией. Например, пути к файлам, личный контекст о работе или ситуации пользователя, имена и значения колонок, названия компаний, URL. Немного предыстории. Некоторые могут быть в нижнем регистре или содержать сокращения, опечатки или разговорную речь. Используй смесь разной длины и фокусируйся на граничных случаях, а не делай их очевидными (пользователь получит шанс их утвердить).

Плохо: `"Format this data"`, `"Extract text from PDF"`, `"Create a chart"`

Хорошо: `"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

Для запросов **should-trigger** (8-10) думай о покрытии. Нужны разные формулировки одного намерения — одни формальные, другие разговорные. Включай случаи, где пользователь явно не называет скилл или тип файла, но явно в нём нуждается. Добавь несколько необычных случаев использования и случаев, где этот скилл конкурирует с другим, но должен победить.

Для запросов **should-not-trigger** (8-10) самые ценные — близкие промахи: запросы, разделяющие ключевые слова или концепции со скиллом, но на самом деле нуждающиеся в чём-то другом. Думай о смежных доменах, неоднозначных формулировках, где наивное совпадение по ключевым словам сработало бы, хотя не должно, и случаях, где запрос затрагивает то, что скилл делает, но в контексте, где уместнее другой инструмент.

Ключевое, чего избегать: не делай should-not-trigger запросы очевидно нерелевантными. «Write a fibonacci function» как негативный тест для PDF-скилла — слишком легко, это ничего не проверяет. Негативные случаи должны быть по-настоящему каверзными.

### Шаг 2: Ревью с пользователем

Представь набор eval пользователю для ревью, используя HTML-шаблон:

1. Прочитай шаблон из `assets/eval_review.html`
2. Замени плейсхолдеры:
   - `__EVAL_DATA_PLACEHOLDER__` → JSON-массив элементов eval (без кавычек вокруг — это присваивание JS-переменной)
   - `__SKILL_NAME_PLACEHOLDER__` → имя скилла
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → текущее описание скилла
3. Запиши во временный файл (например, `/tmp/eval_review_<skill-name>.html`) и открой его: `open /tmp/eval_review_<skill-name>.html`
4. Пользователь может редактировать запросы, переключать should-trigger, добавлять/удалять записи, затем нажать «Export Eval Set»
5. Файл скачивается в `~/Downloads/eval_set.json` — проверь папку Downloads на предмет самой свежей версии на случай, если их несколько (например, `eval_set (1).json`)

Этот шаг важен — плохие eval-запросы ведут к плохим описаниям.

### Шаг 3: Запусти цикл оптимизации

Скажи пользователю: «Это займёт некоторое время — я запущу цикл оптимизации в фоне и буду периодически проверять его.»

Сохрани набор eval в workspace, затем запусти в фоне:

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

Используй ID модели из своего системного промпта (ту, что питает текущую сессию), чтобы тест срабатывания соответствовал тому, что пользователь реально испытывает.

Пока цикл работает, периодически смотри хвост вывода, чтобы давать пользователю обновления о том, на какой итерации он находится и как выглядят оценки.

Это обрабатывает весь цикл оптимизации автоматически. Он делит набор eval на 60% train и 40% held-out test, оценивает текущее описание (прогоняя каждый запрос 3 раза для надёжной частоты срабатывания), затем вызывает Claude, чтобы предложить улучшения на основе того, что провалилось. Он переоценивает каждое новое описание и на train, и на test, итерируя до 5 раз. По завершении он открывает HTML-отчёт в браузере, показывающий результаты по итерациям, и возвращает JSON с `best_description` — выбранным по оценке test, а не train, чтобы избежать оверфиттинга.

### Как работает срабатывание скиллов

Понимание механизма срабатывания помогает проектировать лучшие eval-запросы. Скиллы появляются в списке `available_skills` у Claude с их name + description, и Claude решает, обращаться ли к скиллу, на основе этого описания. Важно знать: Claude обращается к скиллам только для задач, которые не может легко обработать сам — простые одношаговые запросы вроде «прочитай этот PDF» могут не вызвать скилл, даже если описание идеально совпадает, потому что Claude может обработать их напрямую базовыми инструментами. Сложные, многошаговые или специализированные запросы надёжно вызывают скиллы, когда описание совпадает.

Это означает, что твои eval-запросы должны быть достаточно содержательными, чтобы Claude действительно выиграл от обращения к скиллу. Простые запросы вроде «прочитай файл X» — плохие тест-кейсы: они не вызовут скиллы независимо от качества описания.

### Шаг 4: Примени результат

Возьми `best_description` из вывода JSON и обнови frontmatter SKILL.md скилла. Покажи пользователю до/после и сообщи оценки.

## Инструкции, специфичные для Claude.ai

В Claude.ai основной рабочий процесс тот же (черновик → тест → ревью → улучшение → повтор), но поскольку в Claude.ai нет субагентов, некоторая механика меняется. Вот что адаптировать:

**Прогон тест-кейсов**: Отсутствие субагентов означает отсутствие параллельного выполнения. Для каждого тест-кейса прочитай SKILL.md скилла, затем следуй его инструкциям, чтобы выполнить тестовый промпт самостоятельно. Делай их по одному. Это менее строго, чем независимые субагенты (ты написал скилл и ты же его прогоняешь, так что у тебя полный контекст), но это полезная проверка на здравость — а шаг человеческого ревью компенсирует. Пропусти baseline-прогоны — просто используй скилл, чтобы выполнить задачу, как запрошено.

**Ревью результатов**: Если не можешь открыть браузер (например, у VM Claude.ai нет дисплея или ты на удалённом сервере), полностью пропусти браузерный просмотрщик. Вместо этого представь результаты прямо в разговоре. Для каждого тест-кейса покажи промпт и вывод. Если вывод — файл, который пользователю нужно увидеть (вроде .docx или .xlsx), сохрани его в файловую систему и скажи, где он, чтобы пользователь мог скачать и просмотреть. Проси обратную связь инлайн: «Как это выглядит? Что-то бы изменил?»

**Бенчмаркинг**: Пропусти количественный бенчмаркинг — он опирается на сравнения с baseline, которые не имеют смысла без субагентов. Сфокусируйся на качественной обратной связи от пользователя.

**Цикл итерации**: Как и раньше — улучши скилл, перезапусти тест-кейсы, попроси обратную связь — просто без браузерного просмотрщика посередине. Ты всё ещё можешь организовывать результаты в каталоги итераций в файловой системе, если она у тебя есть.

**Оптимизация описания**: Этот раздел требует CLI-инструмент `claude` (в частности, `claude -p`), который доступен только в Claude Code. Пропусти его, если ты в Claude.ai.

**Слепое сравнение**: Требует субагентов. Пропусти.

**Упаковка**: Скрипт `package_skill.py` работает везде, где есть Python и файловая система. В Claude.ai ты можешь запустить его, и пользователь сможет скачать получившийся `.skill`-файл.

**Обновление существующего скилла**: Пользователь может просить обновить существующий скилл, а не создать новый. В этом случае:
- **Сохрани оригинальное имя.** Обрати внимание на имя каталога скилла и поле `name` во frontmatter — используй их без изменений. Например, если установленный скилл — `research-helper`, вывод должен быть `research-helper.skill` (не `research-helper-v2`).
- **Скопируй в доступное для записи место перед редактированием.** Путь установленного скилла может быть только для чтения. Скопируй в `/tmp/skill-name/`, редактируй там и упаковывай из копии.
- **Если упаковываешь вручную, сначала подготовь в `/tmp/`**, затем скопируй в выходной каталог — прямые записи могут провалиться из-за прав доступа.

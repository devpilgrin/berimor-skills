# Режим планирования

Используй, когда пользователь хочет план вместо исполнения.

## Базовое поведение

В этом ходу ты ТОЛЬКО планируешь:

- Не реализуй код.
- Не редактируй файлы проекта, кроме markdown-файла плана.
- Не запускай мутирующие команды, не коммить, не пушь, не выполняй внешних
  действий.
- Можно инспектировать репозиторий и контекст командами только для чтения.
- Результат — markdown-план в активном воркспейсе под `.berimor/plans/`.

## Требования к результату

Напиши конкретный, действенный markdown-план. Включи, когда уместно:

- Цель
- Текущий контекст / допущения
- Предлагаемый подход
- Пошаговый план
- Файлы, которые вероятно изменятся
- Тесты / валидация
- Риски, компромиссы, открытые вопросы

Если задача про код — включи точные пути файлов, вероятные цели тестов и шаги
проверки.

## Куда сохранять

Сохрани план через files.write по пути:

- `.berimor/plans/YYYY-MM-DD_HHMMSS-<slug>.md`

Путь относителен активной рабочей директории. Если окружение задаёт конкретный
целевой путь — используй его. Иначе создай осмысленное имя с меткой времени
под `.berimor/plans/` сам.

## Стиль взаимодействия

- Запрос достаточно ясен — пиши план сразу.
- Вышли `/plan` без явной инструкции — выведи задачу из контекста диалога.
- Действительно недоопределено — задай короткий уточняющий вопрос, не гадай.
- После сохранения кратко ответь, что запланировал, и путь к файлу.

# Как написать хороший план

Пиши полный план реализации в расчёте на исполнителя с нулевым контекстом
кодовой базы и сомнительным вкусом. Документируй всё нужное: какие файлы
трогать, полный код, команды тестирования, какие доки читать, как проверить.
Давай задачи укусного размера. DRY. YAGNI. TDD. Частые коммиты.

**Ключевой принцип:** хороший план делает реализацию очевидной. Если приходится
гадать — план неполон.

## Когда полный план реализации нужен

**Всегда перед:** многошаговыми фичами; разбором сложных требований;
делегированием субагентам.

**Не пропускай, когда:** фича «простая» (допущения порождают баги);
реализуешь сам (будущему тебе нужны указания); работаешь один (документация
важна).

## Гранулярность задач

**Каждая задача = 2–5 минут сфокусированной работы.**

Каждый шаг — одно действие: «напиши падающий тест» — шаг; «запусти и убедись
в падении» — шаг; «реализуй минимум для прохождения» — шаг; «прогони тесты» —
шаг; «закоммить» — шаг.

**Слишком крупно:**
```markdown
### Задача 1: Построить систему аутентификации
[50 строк кода в 5 файлах]
```

**Правильный размер:**
```markdown
### Задача 1: Создать модель User с полем email
[10 строк, 1 файл]

### Задача 2: Добавить поле password hash в User
[8 строк, 1 файл]

### Задача 3: Создать утилиту хеширования паролей
[15 строк, 1 файл]
```

## Структура документа плана

### Шапка (обязательна)

```markdown
# План реализации: [название фичи]

**Цель:** [одно предложение — что строим]

**Архитектура:** [2–3 предложения о подходе]

**Стек:** [ключевые технологии/библиотеки]

---
```

### Структура задачи

````markdown
### Задача N: [описательное имя]

**Цель:** чего достигает задача (одно предложение)

**Файлы:**
- Создать: `exact/path/to/new_file.py`
- Изменить: `exact/path/to/existing.py:45-67` (строки, если известны)
- Тест: `tests/path/to/test_file.py`

**Шаг 1: Напиши падающий тест**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

**Шаг 2: Запусти тест — убедись в падении**

Запуск: `pytest tests/path/test.py::test_specific_behavior -v`
Ожидается: FAIL — "function not defined"

**Шаг 3: Минимальная реализация**

```python
def function(input):
    return expected
```

**Шаг 4: Запусти тест — убедись в прохождении**

Запуск: `pytest tests/path/test.py::test_specific_behavior -v`
Ожидается: PASS

**Шаг 5: Коммит**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## Процесс написания

### Шаг 1: Пойми требования

Прочитай и пойми: требования к фиче, дизайн-документы или описание
пользователя, критерии приёмки, ограничения.

### Шаг 2: Исследуй кодовую базу

```python
# Структура проекта
search_files("*.py", target="files", path="src/")

# Похожие фичи
search_files("similar_pattern", path="src/", file_glob="*.py")

# Существующие тесты
search_files("*.py", target="files", path="tests/")

# Ключевые файлы
read_file("src/app.py")
```

### Шаг 3: Спроектируй подход

Реши: архитектурный паттерн, организацию файлов, нужные зависимости,
стратегию тестирования.

### Шаг 4: Напиши задачи

В порядке: инфраструктура/setup → основная функциональность (TDD на каждую) →
граничные случаи → интеграция → чистка/документация.

### Шаг 5: Добавь полные детали

Для каждой задачи: **точные пути файлов** (не «конфиг», а
`src/config/settings.py`); **полные примеры кода** (не «добавь валидацию», а
сам код); **точные команды** с ожидаемым выводом; **шаги верификации**,
доказывающие, что задача работает.

### Шаг 6: Проверь план

- [ ] Задачи последовательны и логичны
- [ ] Каждая задача укусного размера (2–5 мин)
- [ ] Пути файлов точные
- [ ] Примеры кода полные (copy-paste)
- [ ] Команды точные, с ожидаемым выводом
- [ ] Нет недостающего контекста
- [ ] Применены DRY, YAGNI, TDD

## Принципы

### DRY (Don't Repeat Yourself)

**Плохо:** валидация скопипащена в 3 местах. **Хорошо:** вынеси функцию,
используй везде.

### YAGNI (You Aren't Gonna Need It)

**Плохо:** «гибкость» под будущие требования. **Хорошо:** только то, что нужно
сейчас.

```python
# Плохо — нарушение YAGNI
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
        self.preferences = {}  # Пока не нужно!
        self.metadata = {}     # Пока не нужно!

# Хорошо — YAGNI
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
```

### TDD

Каждая задача, порождающая код, включает полный цикл TDD: падающий тест →
проверка падения → минимальный код → проверка прохождения. Подробности — в
скилле `test-driven-development`.

### Частые коммиты

Коммить после каждой задачи:

```bash
git add [files]
git commit -m "type: description"
```

## Типовые ошибки

### Размытые задачи

**Плохо:** «Добавь аутентификацию»
**Хорошо:** «Создай модель User с полями email и password_hash»

### Неполный код

**Плохо:** «Шаг 1: Добавь функцию валидации»
**Хорошо:** тот же шаг + полный код функции

### Нет верификации

**Плохо:** «Шаг 3: Проверь, что работает»
**Хорошо:** «Шаг 3: Запусти `pytest tests/test_auth.py -v`, ожидается: 3 passed»

### Нет путей файлов

**Плохо:** «Создай файл модели»
**Хорошо:** «Создать: `src/models/user.py`»

## Передача на исполнение

После сохранения плана предложи вариант исполнения:

**«План готов и сохранён. Могу исполнить его по задачам: отдельный субагент
(agents.run) на каждую задачу, с проверкой результата после каждой.
Приступить?»**

При исполнении: свежий субагент на задачу с полным контекстом; проверка
соответствия плану после каждой задачи; переход дальше только после одобрения.

## Запомни

```
Задачи укусного размера (2–5 мин каждая)
Точные пути файлов
Полный код (copy-paste)
Точные команды с ожидаемым выводом
Шаги верификации
DRY, YAGNI, TDD
Частые коммиты
```

**Хороший план делает реализацию очевидной.**

# Руководство по разработке MCP-серверов

## Обзор

Создавай MCP-серверы (Model Context Protocol), позволяющие LLM взаимодействовать с внешними сервисами через хорошо спроектированные инструменты. Качество MCP-сервера измеряется тем, насколько хорошо он позволяет LLM выполнять реальные задачи.

---

# Процесс

## 🚀 Высокоуровневый рабочий процесс

Создание качественного MCP-сервера включает четыре основные фазы:

### Фаза 1: Глубокое исследование и планирование

#### 1.1 Пойми современный дизайн MCP

**Покрытие API vs. инструменты рабочих процессов:**
Балансируй между полным покрытием эндпоинтов API и специализированными инструментами рабочих процессов. Инструменты рабочих процессов могут быть удобнее для конкретных задач, а полное покрытие даёт агентам гибкость комбинировать операции. Производительность зависит от клиента — одним клиентам помогает выполнение кода, объединяющего базовые инструменты, другие лучше работают с высокоуровневыми рабочими процессами. Если сомневаешься, отдавай приоритет полному покрытию API.

**Именование и обнаруживаемость инструментов:**
Понятные, описательные имена инструментов помогают агентам быстро находить нужные. Используй последовательные префиксы (например, `github_create_issue`, `github_list_repos`) и именование, ориентированное на действие.

**Управление контекстом:**
Агентам помогают лаконичные описания инструментов и возможность фильтровать/пагинировать результаты. Проектируй инструменты, возвращающие сфокусированные, релевантные данные. Некоторые клиенты поддерживают выполнение кода, что помогает агентам эффективно фильтровать и обрабатывать данные.

**Действенные сообщения об ошибках:**
Сообщения об ошибках должны направлять агентов к решению — с конкретными предложениями и следующими шагами.

#### 1.2 Изучи документацию протокола MCP

**Навигация по спецификации MCP:**

Начни с карты сайта, чтобы найти нужные страницы: `https://modelcontextprotocol.io/sitemap.xml`

Затем запрашивай конкретные страницы с суффиксом `.md` для формата markdown (например, `https://modelcontextprotocol.io/specification/draft.md`).

Ключевые страницы для изучения:
- Обзор спецификации и архитектура
- Транспортные механизмы (streamable HTTP, stdio)
- Определения инструментов, ресурсов и промптов

#### 1.3 Изучи документацию фреймворка

**Рекомендуемый стек:**
- **Язык**: TypeScript (качественная поддержка SDK и хорошая совместимость во многих средах выполнения, например MCPB. Кроме того, AI-модели хорошо генерируют TypeScript-код благодаря его широкой распространённости, статической типизации и хорошим инструментам линтинга)
- **Транспорт**: Streamable HTTP для удалённых серверов, с использованием stateless JSON (проще масштабировать и поддерживать, в отличие от stateful-сессий и потоковых ответов). stdio для локальных серверов.

**Загрузи документацию фреймворка:**

- **MCP Best Practices**: [📋 View Best Practices](./reference/mcp_best_practices.md) - Основные руководства

**Для TypeScript (рекомендуется):**
- **TypeScript SDK**: Используй WebFetch для загрузки `https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/README.md`
- [⚡ TypeScript Guide](./reference/node_mcp_server.md) - Паттерны и примеры TypeScript

**Для Python:**
- **Python SDK**: Используй WebFetch для загрузки `https://raw.githubusercontent.com/modelcontextprotocol/python-sdk/main/README.md`
- [🐍 Python Guide](./reference/python_mcp_server.md) - Паттерны и примеры Python

#### 1.4 Спланируй реализацию

**Изучи API:**
Просмотри документацию API сервиса, чтобы выявить ключевые эндпоинты, требования к аутентификации и модели данных. Используй веб-поиск и WebFetch по необходимости.

**Выбор инструментов:**
Отдавай приоритет полному покрытию API. Составь список эндпоинтов для реализации, начиная с самых распространённых операций.

### Фаза 2: Реализация

#### 2.1 Настрой структуру проекта

См. языкоспецифичные руководства по настройке проекта:
- [⚡ TypeScript Guide](./reference/node_mcp_server.md) - Структура проекта, package.json, tsconfig.json
- [🐍 Python Guide](./reference/python_mcp_server.md) - Организация модулей, зависимости

#### 2.2 Реализуй базовую инфраструктуру

Создай общие утилиты:
- API-клиент с аутентификацией
- Хелперы обработки ошибок
- Форматирование ответов (JSON/Markdown)
- Поддержка пагинации

#### 2.3 Реализуй инструменты

Для каждого инструмента:

**Входная схема:**
- Используй Zod (TypeScript) или Pydantic (Python)
- Включай ограничения и понятные описания
- Добавляй примеры в описания полей

**Выходная схема:**
- Определяй `outputSchema` где возможно для структурированных данных
- Используй `structuredContent` в ответах инструментов (возможность TypeScript SDK)
- Помогает клиентам понимать и обрабатывать вывод инструментов

**Описание инструмента:**
- Лаконичное резюме функциональности
- Описания параметров
- Схема возвращаемого типа

**Реализация:**
- Async/await для операций ввода-вывода
- Корректная обработка ошибок с действенными сообщениями
- Поддержка пагинации где применимо
- Возвращай и текстовое содержимое, и структурированные данные при использовании современных SDK

**Аннотации:**
- `readOnlyHint`: true/false
- `destructiveHint`: true/false
- `idempotentHint`: true/false
- `openWorldHint`: true/false

### Фаза 3: Ревью и тестирование

#### 3.1 Качество кода

Проверь:
- Отсутствие дублирования кода (принцип DRY)
- Последовательная обработка ошибок
- Полное покрытие типами
- Понятные описания инструментов

#### 3.2 Сборка и тестирование

**TypeScript:**
- Запусти `npm run build` для проверки компиляции
- Протестируй с MCP Inspector: `npx @modelcontextprotocol/inspector`

**Python:**
- Проверь синтаксис: `python -m py_compile your_server.py`
- Протестируй с MCP Inspector

См. языкоспецифичные руководства для детальных подходов к тестированию и чек-листов качества.

### Фаза 4: Создание оценок

После реализации MCP-сервера создай комплексные оценки для проверки его эффективности.

**Загрузи [✅ Evaluation Guide](./reference/evaluation.md) для полных руководств по оценке.**

#### 4.1 Пойми цель оценки

Используй оценки, чтобы проверить, могут ли LLM эффективно использовать твой MCP-сервер для ответа на реалистичные, сложные вопросы.

#### 4.2 Создай 10 оценочных вопросов

Чтобы создать эффективные оценки, следуй процессу, описанному в руководстве по оценке:

1. **Инспекция инструментов**: Составь список доступных инструментов и пойми их возможности
2. **Исследование содержимого**: Используй READ-ONLY операции для изучения доступных данных
3. **Генерация вопросов**: Создай 10 сложных, реалистичных вопросов
4. **Проверка ответов**: Реши каждый вопрос сам, чтобы проверить ответы

#### 4.3 Требования к оценкам

Убедись, что каждый вопрос:
- **Независим**: Не зависит от других вопросов
- **Read-only**: Требует только недеструктивных операций
- **Сложный**: Требует нескольких вызовов инструментов и глубокого исследования
- **Реалистичный**: Основан на реальных случаях использования, важных для людей
- **Проверяемый**: Единственный, чёткий ответ, который можно проверить сравнением строк
- **Стабильный**: Ответ не изменится со временем

#### 4.4 Формат вывода

Создай XML-файл со следующей структурой:

```xml
<evaluation>
  <qa_pair>
    <question>Find discussions about AI model launches with animal codenames. One model needed a specific safety designation that uses the format ASL-X. What number X was being determined for the model named after a spotted wild cat?</question>
    <answer>3</answer>
  </qa_pair>
<!-- More qa_pairs... -->
</evaluation>
```

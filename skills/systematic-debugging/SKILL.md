# Систематическая отладка

Случайные правки тратят время и создают новые баги. Быстрые заплатки маскируют
лежащую в основе проблему.

**Ключевой принцип:** ВСЕГДА находи первопричину до попыток исправления.
Правка симптома — это провал.

## Железный закон

```
НИКАКИХ ПРАВОК БЕЗ ИССЛЕДОВАНИЯ ПЕРВОПРИЧИНЫ
```

Если фаза 1 не завершена — предлагать исправления нельзя.

## Правило цикла обратной связи

Цикл обратной связи и есть работа по отладке. Прежде чем читать код и строить
теорию, создай или найди **узкую** команду, которая краснеет ровно на симптоме
пользователя и зеленеет, когда баг исправлен. Узкий цикл — быстрый,
детерминированный, запускаемый агентом и достаточно специфичный, чтобы
поймать именно этот баг, — не просто «не падает».

Когда чистое воспроизведение трудно получить, трать непропорционально много
усилий на построение цикла. Гадание без способной покраснеть команды — тот
режим отказа, против которого этот скилл и существует.

## Когда использовать

Для ЛЮБОЙ технической проблемы: падающие тесты, баги в проде, неожиданное
поведение, проблемы производительности, сбои сборки, интеграционные проблемы.

**ОСОБЕННО используй, когда:**
- жмёт время (в аврале так и тянет гадать);
- «быстрая правка» кажется очевидной;
- уже пробовал несколько правок;
- предыдущая правка не сработала;
- не до конца понимаешь проблему.

**Не пропускай, когда:** проблема «простая»; спешишь; кто-то хочет фикс
«прямо сейчас» — систематика быстрее метаний.

## Четыре фазы

Каждую фазу ОБЯЗАТЕЛЬНО завершить до перехода к следующей.

---

## Фаза 1: Исследование первопричины

**ДО любой попытки правки:**

### 1. Внимательно прочитай сообщения об ошибках

- Не пролистывай ошибки и предупреждения — часто в них готовое решение.
- Читай стектрейсы целиком: номера строк, пути файлов, коды ошибок.

**Действие:** files.read по затронутым исходникам; files.search — найти строку
ошибки в кодовой базе.

### 2. Построй узкий цикл обратной связи

- Можешь ли ты вызвать точный симптом пользователя одной командой?
- Команда падает на этом баге и проходит только после исправления?
- Достаточно быстра, чтобы гонять повторно? Детерминирована?
- Не воспроизводится → собирай больше данных, не гадай.

**Способы построить цикл — примерно в этом порядке:**

1. **Падающий тест** на шве, достающем до бага: unit, интеграционный, e2e.
2. **HTTP-скрипт / curl** против запущенного dev-сервера.
3. **Вызов CLI** с фикстурой, diff stdout/stderr против ожидаемого.
4. **Headless-браузерный скрипт** (Playwright/Puppeteer) с проверками DOM,
   консоли, сети.
5. **Повтор захваченного трейса**: HAR, тело запроса, лог событий, сообщение
   очереди, webhook.
6. **Одноразовый стенд**, поднимающий минимальный срез системы и вызывающий
   падающий путь.
7. **Property / fuzz-цикл**, когда баг — неверный вывод на широком пространстве
   входов.
8. **Стенд для бисекции** под `git bisect run`, если баг появился между двумя
   известными состояниями.
9. **Дифференциальный цикл**: старая версия против новой, два конфига, два
   провайдера, два набора данных.
10. **Скрипт с человеком в цикле** — только в крайнем случае.

**Ужесточи цикл, когда он появился:**

- Быстрее: кешируй setup, сузь область, отключи лишнюю инициализацию.
- Чётче сигнал: проверяй точный симптом, а не абстрактный успех.
- Детерминированнее: зафиксируй время, сиды, ФС, сеть.

Для недетерминированных багов ближайшая цель — поднять частоту
воспроизведения: запусти триггер 100 раз, распараллель, добавь нагрузку,
сужай временные окна. Флак на 50% отлаживаем; на 1% — обычно нет.

**Действие:** запусти цикл через terminal.exec:

```bash
# Точечный падающий тест
pytest tests/test_module.py::test_name -v

# Или скриптовое воспроизведение
python scripts/repro_bug.py

# Или флаки на высокой частоте повторов
for i in {1..100}; do pytest tests/test_flake.py::test_name -q || break; done
```

### 3. Проверь недавние изменения

```bash
# Недавние коммиты
git log --oneline -10

# Незакоммиченные изменения
git diff

# История конкретного файла
git log -p --follow src/problematic_file.py | head -100
```

### 4. Собери доказательства в многокомпонентных системах

**КОГДА система состоит из нескольких компонентов (API → сервис → БД,
CI → сборка → деплой):**

ДО предложения правок добавь диагностическую инструментацию на КАЖДОЙ границе
компонентов: логируй вход и выход компонента, проверь распространение
конфига/окружения, состояние на каждом слое. Один прогон покажет, ГДЕ ломается.
Потом анализируй доказательства и исследуй конкретный компонент.

### 5. Проследи поток данных

**КОГДА ошибка глубоко в стеке вызовов:**

- Где зарождается плохое значение? Кто вызвал функцию с плохим значением?
- Трассируй вверх, пока не найдёшь источник. Чини в источнике, не в симптоме.

**Действие:** files.search для трассировки ссылок:

```python
# Где вызывается функция
search_files("function_name(", path="src/", file_glob="*.py")

# Где присваивается переменная
search_files("variable_name\\s*=", path="src/", file_glob="*.py")
```

### Чеклист завершения фазы 1

- [ ] Сообщения об ошибках прочитаны и поняты целиком
- [ ] Узкая команда цикла существует и запускалась хотя бы раз
- [ ] Цикл способен краснеть: проверяет точный симптом, а не соседний сбой
- [ ] Цикл детерминирован, либо у флака достаточная частота воспроизведения
- [ ] Недавние изменения выявлены и просмотрены
- [ ] Доказательства собраны (логи, состояние, поток данных)
- [ ] Проблема изолирована до конкретного компонента/кода
- [ ] Гипотезы первопричины можно сформулировать и проверить

**СТОП:** не переходи к фазе 2, пока не понятно, ПОЧЕМУ это происходит.

## Фаза 2: Анализ паттерна

### 0. Минимизируй воспроизведение

Когда цикл красен, ужимай repro до минимального сценария, который всё ещё
красен. Отрезай входы, вызывающих, конфиг, данные, шаги **по одному**,
перезапуская цикл после каждого отрезания. Оставляй только несущее для сбоя.

Готово, когда удаление любого оставшегося элемента делает цикл зелёным.
Минимальный repro сужает пространство гипотез и часто становится чистейшим
регрессионным тестом.

### 1. Найди работающие примеры

- Найди похожий работающий код в той же кодовой базе (files.search).

### 2. Сравни с эталоном

- Если реализуешь паттерн — прочитай эталонную реализацию ПОЛНОСТЬЮ,
  не по диагонали. Понимай паттерн целиком до применения.

### 3. Выяви различия

- Чем работающее отличается от сломанного? Выпиши каждое различие.
- Не считай, что «это не может иметь значения».

### 4. Пойми зависимости

- Какие компоненты, настройки, конфиг, окружение нужны? Какие допущения?

---

## Фаза 3: Гипотезы и проверка

**Научный метод:**

### 1. Сформулируй ранжированные фальсифицируемые гипотезы

- Сгенерируй 3–5 правдоподобных гипотез до проверки любой из них.
- Ранжируй по вероятности и дешевизне фальсификации.
- Сформулируй предсказание каждой: «если причина X, то изменение/наблюдение
  Y должно дать Z».
- Отбрось гипотезу без проверяемого предсказания.

Если пользователь на связи — покажи ранжированный список до проверки: у него
может быть знание домена, мгновенно меняющее порядок.

### 2. Проверяй минимально

- Проверяй гипотезу с наивысшим рангом наименьшим возможным зондом.
- Меняй одну переменную за раз. Не чини несколько вещей сразу.
- Предпочитай отладчик/REPL логам: один брейкпоинт лучше десяти логов.
- Временные логи помечай уникальным префиксом вида `[DEBUG-a4f2]`, чтобы
  уборка была одним поиском.

### 3. Проверь результат до продолжения

- Сработало? → Фаза 4.
- Не сработало? → НОВАЯ гипотеза. НЕ накладывай правки поверх.

### 4. Когда не знаешь

- Скажи «я не понимаю X». Не делай вид, что знаешь. Спроси пользователя.
- Исследуй дальше (web.search, http.fetch — доки, тексты ошибок).

## Фаза 4: Реализация

**Чини первопричину, не симптом:**

### 1. Создай падающий тест

- Простейшее воспроизведение, автоматизированный тест, если возможно.
- ОБЯЗАТЕЛЬНО до правки. См. скилл `test-driven-development`.

### 2. Реализуй одну правку

- Адресуй найденную первопричину. ОДНО изменение за раз.
- Никаких «попутных» улучшений и встроенного рефакторинга.

### 3. Проверь правку

```bash
# Точечный регрессионный тест
pytest tests/test_module.py::test_regression -v

# Полный прогон — без регрессий
pytest tests/ -q
```

### 4. Правка не сработала — правило трёх

- **СТОП.** Посчитай: сколько правок уже пробовал?
- < 3: вернись к фазе 1 с новой информацией.
- **≥ 3: СТОП — поставь под вопрос архитектуру (пункт 5).**
- НЕ пытайся правку №4 без архитектурного обсуждения.

### 5. Если 3+ правок не помогли: под вопросом архитектура

**Признаки архитектурной проблемы:** каждая правка вскрывает новое разделяемое
состояние/связанность в другом месте; правки требуют «массивного
рефакторинга»; каждая правка рождает новые симптомы.

**СТОП и подвергни сомнению основы:** здоров ли паттерн в принципе? Держимся
по инерции? Рефакторить архитектуру или дальше лечить симптомы?

**Обсуди с пользователем до новых попыток.** Это не провалившаяся гипотеза —
это неверная архитектура.

## Красные флаги — СТОП и вернись к процессу

Если ловишь себя на мысли:

- «Быстро починю, разберёмся потом»
- «Просто попробую поменять X и посмотрю»
- «Внесу несколько изменений и прогоню тесты»
- «Пропущу тест, проверю вручную»
- «Наверное, это X, поправлю»
- «Не до конца понимаю, но может сработать»
- «Вот основные проблемы: [список правок без исследования]»
- **«Ещё одна попытка» (после 2+ неудачных)**
- **Каждая правка вскрывает новую проблему в другом месте**

**ВСЁ это значит: СТОП. Возвращайся к фазе 1.**

**Если 3+ правок не помогли:** под вопросом архитектура (фаза 4, пункт 5).

## Типовые самооправдания

| Отговорка | Реальность |
|-----------|-----------|
| «Проблема простая, процесс не нужен» | У простых багов тоже есть первопричина. Процесс быстр для простых багов. |
| «Авария, нет времени на процесс» | Систематика БЫСТРЕЕ, чем метания «попробуй-проверь». |
| «Сначала попробую, потом исследую» | Первая правка задаёт паттерн. Делай правильно сразу. |
| «Тест напишу после того, как правка заработает» | Непокрытые правки не держатся. Тест первым это доказывает. |
| «Несколько правок сразу экономит время» | Не изолировать, что сработало. Порождает новые баги. |
| «Эталон длинный, адаптирую паттерн» | Частичное понимание гарантирует баги. Читай целиком. |
| «Я вижу проблему, сейчас поправлю» | Видеть симптомы ≠ понимать первопричину. |
| «Ещё одна попытка» (после 2+ неудач) | 3+ неудачи = архитектурная проблема. Сомневайся в паттерне, не чини снова. |

## Быстрая шпаргалка

| Фаза | Ключевые действия | Критерий успеха |
|------|-------------------|-----------------|
| **1. Первопричина** | Читай ошибки, воспроизведи, проверь изменения, собери доказательства, проследи данные | Понятно ЧТО и ПОЧЕМУ |
| **2. Паттерн** | Найди рабочие примеры, сравни, выяви различия | Известно, чем отличается |
| **3. Гипотеза** | Сформулируй теорию, проверь минимально, одна переменная | Подтверждено или новая гипотеза |
| **4. Реализация** | Регрессионный тест, правка первопричины, верификация | Баг закрыт, все тесты зелёные |

## Делегирование исследования

Для сложной многокомпонентной отладки запусти исследовательского субагента
через agents.run:

```
Задача: Исследуй, почему падает [конкретный тест/поведение].
Следуй скиллу systematic-debugging:
1. Внимательно прочитай сообщение об ошибке
2. Воспроизведи проблему
3. Проследи поток данных до первопричины
4. Доложи находки — НЕ чини пока

Ошибка: [полный текст]
Файл: [путь к падающему коду]
Команда теста: [точная команда]
```

## Связка с test-driven-development

При исправлении багов: напиши тест, воспроизводящий баг (RED) → систематически
найди первопричину → почини её (GREEN). Тест доказывает правку и защищает от
регрессии.

**Без сокращений. Без гадания. Систематика всегда выигрывает.**

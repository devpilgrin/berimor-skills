# Разработка через тестирование (TDD)

Сначала напиши тест. Увидь его падение. Напиши минимальный код, чтобы он
прошёл.

**Ключевой принцип:** если ты не видел падение теста — ты не знаешь, проверяет
ли он то, что нужно.

## Когда использовать

**Всегда:** новые фичи, исправления багов, рефакторинг, изменения поведения.

**Исключения (сначала спроси пользователя):** одноразовые прототипы,
сгенерированный код, конфигурационные файлы.

Думаешь «пропущу TDD только в этот раз»? Стоп. Это рационализация.

## Железный закон

```
НИКАКОГО ПРОДАКШН-КОДА БЕЗ ПАДАЮЩЕГО ТЕСТА СНАЧАЛА
```

Написал код до теста? Удали его. Начни заново.

**Без исключений:** не оставляй «для справки», не «адаптируй» во время
написания тестов, не подглядывай. Удалить значит удалить. Реализуй заново,
от тестов.

## Цикл Red-Green-Refactor

### RED — напиши падающий тест

Один минимальный тест, показывающий, что должно происходить.

**Хороший тест:**
```python
def test_retries_failed_operations_3_times():
    attempts = 0
    def operation():
        nonlocal attempts
        attempts += 1
        if attempts < 3:
            raise Exception('fail')
        return 'success'

    result = retry_operation(operation)

    assert result == 'success'
    assert attempts == 3
```
Ясное имя, реальное поведение, одна вещь.

**Плохой тест:**
```python
def test_retry_works():
    mock = MagicMock()
    mock.side_effect = [Exception(), Exception(), 'success']
    result = retry_operation(mock)
    assert result == 'success'  # А число попыток? Тайминги?
```
Размытое имя, тестирует мок, а не реальный код.

**Требования:**
- Одно поведение на тест.
- Ясное описательное имя (есть «и» в имени? Раздели).
- Реальный код, не моки (если только действительно без них нельзя).
- Имя описывает поведение, не реализацию.

### Проверь RED — увидь падение

**ОБЯЗАТЕЛЬНО. Никогда не пропускай.**

```bash
# Запусти точечный тест через terminal.exec
pytest tests/test_feature.py::test_specific_behavior -v
```

Убедись: тест падает (не ошибка от опечатки); сообщение о падении ожидаемое;
падает, потому что фичи нет.

**Тест прошёл сразу?** Ты тестируешь существующее поведение. Исправь тест.

**Тест падает с ошибкой?** Исправь ошибку, перезапускай, пока не будет
правильного падения.

### GREEN — минимальный код

Простейший код, чтобы тест прошёл. Ничего больше.

**Хорошо:**
```python
def add(a, b):
    return a + b  # Ничего лишнего
```

**Плохо:**
```python
def add(a, b):
    result = a + b
    logging.info(f"Adding {a} + {b} = {result}")  # Лишнее!
    return result
```

Не добавляй фичи, не рефактори соседний код, не «улучшай» сверх теста.

**В GREEN хитрить можно:** захардкодить возврат, скопипастить, продублировать
код, пропустить граничные случаи. Починим в REFACTOR.

### Проверь GREEN — увидь успех

**ОБЯЗАТЕЛЬНО.**

```bash
# Точечный тест
pytest tests/test_feature.py::test_specific_behavior -v

# Затем ВСЕ тесты — проверка на регрессии
pytest tests/ -q
```

Убедись: тест проходит; остальные тесты проходят; вывод чистый (без ошибок и
предупреждений).

**Тест упал?** Чини код, не тест. **Упали другие тесты?** Чини регрессии
сейчас.

### REFACTOR — наведи чистоту

Только после зелёного: убери дублирование, улучши имена, выдели хелперы,
упрости выражения. Тесты остаются зелёными на всём протяжении. Не добавляй
поведение.

**Тесты упали во время рефакторинга?** Немедленно откати. Шаги мельче.

### Повторяй

Следующий падающий тест для следующего поведения. Один цикл за раз.

## Избегай горизонтальных срезов

**Не** пиши сначала все тесты, потом всю реализацию. Это горизонтальная
нарезка: RED превращается в «кучу воображаемых тестов», GREEN — в «заставь
кучу пройти». Получаются хрупкие тесты, спроектированные до того, как
реализация научила тебя, какие поведение и интерфейс действительно важны.

Используй вертикальные «трассирующие пули»:

```text
НЕПРАВИЛЬНО:
  RED:   test1, test2, test3, test4
  GREEN: impl1, impl2, impl3, impl4

ПРАВИЛЬНО:
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

Трассирующая пуля — один сквозной срез поведения: доказывает, что путь
работает, учит интерфейсу и заземляет каждый следующий тест на только что
узнанном.

## Почему порядок важен

**«Напишу тесты после, чтобы проверить, что работает»** — тесты, написанные
после кода, проходят сразу. А мгновенный успех ничего не доказывает: может,
проверяется не то; может, реализация, а не поведение; могут быть пропущены
граничные случаи; ты никогда не видел, как тест ловит баг.

**«Я вручную проверил все граничные случаи»** — ручная проверка ad-hoc: нет
записи, что проверял; нельзя перезапустить после изменений; под давлением
легко забыть случаи. «Работало, когда я пробовал» ≠ полноценно.

**«Удалять X часов работы — расточительно»** — ошибка невозвратных затрат.
Время уже потрачено. Выбор сейчас: удалить и переписать через TDD (высокая
уверенность) или оставить и дописать тесты после (низкая уверенность, вероятны
баги). Настоящая трата — код, которому нельзя доверять.

**«TDD — догма, прагматик адаптирует»** — TDD и ЕСТЬ прагматика: баги находятся
до коммита; регрессии предотвращаются; тесты документируют поведение;
рефакторинг безопасен. «Прагматичные» сокращения = отладка в проде = медленнее.

**«Тесты после дают те же цели — важен дух, не ритуал»** — нет. Тесты-после
отвечают «что это делает?». Тесты-первыми — «что это должно делать?». Тесты
после смещены твоей реализацией: ты проверяешь то, что построил, а не то, что
требуется.

## Типовые самооправдания

| Отговорка | Реальность |
|-----------|-----------|
| «Слишком просто для теста» | Простой код ломается. Тест — 30 секунд. |
| «Протестирую после» | Мгновенно зелёные тесты ничего не доказывают. |
| «Уже проверил вручную» | Ad-hoc ≠ систематично. Нет записи, не перезапустить. |
| «Удалять X часов — жаль» | Ошибка невозвратных затрат. Непроверенный код — техдолг. |
| «Оставлю как референс, тесты напишу первыми» | Ты его адаптируешь. Это и есть «тесты после». Удалить значит удалить. |
| «Надо сначала поисследовать» | Ок. Выбрось исследование, начни с TDD. |
| «Тест труден = дизайн неясен» | Слушай тест. Трудно тестировать = трудно использовать. |
| «TDD замедлит меня» | TDD быстрее отладки. Прагматично = тест-первым. |
| «В существующем коде нет тестов» | Ты его улучшаешь. Добавь тесты на код, который трогаешь. |

## Красные флаги — СТОП и начни заново

Если ловишь себя на любом из этого — удали код и перезапусти TDD:

- код до теста; тест после реализации;
- тест прошёл с первого запуска;
- не можешь объяснить, почему тест упал;
- тесты добавлены «потом»;
- «только в этот раз»; «я уже вручную проверил»;
- «оставлю как референс» / «адаптирую существующий код»;
- «уже потратил X часов, удалять жаль»;
- «TDD — догма, я прагматик»;
- «это другое, потому что...»

**Всё это значит: удали код. Начни заново с TDD.**

## Чеклист верификации

Перед тем как считать работу завершённой:

- [ ] У каждой новой функции/метода есть тест
- [ ] Видел падение каждого теста до реализации
- [ ] Каждый тест падал по ожидаемой причине (нет фичи, не опечатка)
- [ ] Писал минимальный код для прохождения каждого теста
- [ ] Все тесты проходят
- [ ] Вывод чистый (без ошибок, предупреждений)
- [ ] Тесты используют реальный код (моки — только если без них никак)
- [ ] Покрыты граничные случаи и ошибки

Не можешь отметить всё? Ты пропустил TDD. Начни заново.

## Когда застрял

| Проблема | Решение |
|----------|---------|
| Не знаю, как тестировать | Напиши желаемый API. Напиши assert первым. Спроси пользователя. |
| Тест слишком сложный | Слишком сложный дизайн. Упрости интерфейс. |
| Приходится мокать всё | Код слишком связан. Внедряй зависимости. |
| Огромный setup теста | Выдели хелперы. Всё ещё сложно? Упрощай дизайн. |

## Делегирование реализации

При отправке субагентов на реализацию требуй TDD прямо в задаче (agents.run):

```
Задача: Реализуй [фичу] строго по TDD:
1. СНАЧАЛА напиши падающий тест
2. Запусти — убедись, что падает
3. Напиши минимальный код для прохождения
4. Запусти — убедись, что проходит
5. Отрефактори при необходимости
6. Закоммить

Команда тестов проекта: pytest tests/ -q
Структура проекта: [опиши релевантные файлы]
```

## Антипаттерны тестирования

- **Тестирование поведения моков вместо реального поведения** — моки проверяют
  взаимодействия, а не заменяют тестируемую систему.
- **Тестирование деталей реализации** — проверяй поведение/результаты, не
  внутренние вызовы методов.
- **Только happy path** — всегда граничные случаи, ошибки, границы.
- **Хрупкие тесты** — тесты проверяют поведение, не структуру; рефакторинг не
  должен их ломать.

## Финальное правило

```
Продакшн-код → тест существует и сначала падал
Иначе → это не TDD
```

Без исключений — только с явного разрешения пользователя.
